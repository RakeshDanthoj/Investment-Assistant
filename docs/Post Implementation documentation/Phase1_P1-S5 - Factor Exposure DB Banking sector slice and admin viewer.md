# Post Implementation Detailed Document — P1-S5

**Version:** v1.0 | **Date:** 17-05-2026  
**Story ID:** P1-S5 (Phase 1, Story 5)  
**Reference plan:** `docs/plans/finnwise-phase1-implementation-tasks.md`

---

We finished the first vertical slice of the Factor Exposure Database the PRD calls Tier 1 data. The goal was never to model the whole market in Phase 1—it was to give the card pipeline and editors something *real* to query: a banking-sector grid of instruments crossed against the eight macro factors, every cell tagged with MMJ classification and a source URL so nothing floats in the narrative without traceability.

On the database side we added four tables—sectors, factors, instruments, and a sensitivity join table with a composite primary key so each bank/factor pair appears once. MMJ tags reuse the existing Postgres enum from earlier schema work; sensitivities are stored as signed integers in a fixed range, which keeps the API and any future LLM validators simple. We ship RLS on these tables but deliberately do not open permissive policies for the anon role, because the app reads this data through the Python backend with a direct Postgres URL rather than exposing the matrix through PostgREST.

The seed is the other half of the story. Banking gets fifteen NSE-listed names with ISINs, and every name gets all eight factors—that is 120 sensitivity rows. The SQL file is generated by a small script so we can regenerate safely and diff changes; the numbers are deterministic placeholders meant for integration testing and demos, not for anyone to interpret as research output until the Product Owner replaces them with reviewed assumptions.

The API surface is intentionally small. Any authenticated caller (Supabase Bearer token) can fetch a single cell: ticker, factor slug, sensitivity, MMJ, source link, retrieved time, plus a freshness band derived from age—green, amber, or red—aligned with how Evidence treats stale human-sourced inputs. A second endpoint returns the full matrix for a sector, but only for emails on an environment-configured allow list. That duplicates the check on the Next.js admin page for usability; the backend check is what actually protects the data.

The internal UI lives at `/admin/factor-db`. It is a dense table: sticky instrument column, eight factor columns, two dots per cell (MMJ colour and freshness), and a dropdown to mute non-selected factor columns when you want to review one axis at a time. Session handling follows the rest of the app—if you are not signed in you go to the sign-in flow with a return path; if you are signed in but not on the list you see a clear forbidden message rather than a broken grid.

**If you operate this in an environment:** apply the factor-db migration after the existing event-related migration in the chain, run the banking seed once, set `SUPABASE_DB_URL` on the API, mirror `FACTOR_DB_ADMIN_EMAILS` between frontend and backend config, and point `NEXT_PUBLIC_API_BASE_URL` at the API so the server component can fetch the matrix.

**What this unlocks next:** downstream stories that draft cards from events can pull real sensitivity rows instead of mocks, and the editorial story can sanity-check coverage from the same viewer the Product Owner uses.

**One thing not to forget:** treat the current seed as scaffolding until editorial replaces it—the constraints and APIs are the durable part; the numeric cells are easy to regenerate but should be reviewed before any external tester reads them as “the model.”

**What this story aimed to achieve (plain language)**

FinnWise needs a structured “Factor Exposure Database” so the card pipeline and editorial process can ground narrative in tagged macro sensitivities instead of invented numbers. This story delivers: (1) the relational schema for sectors, instruments, eight canonical macro factors, and per-cell sensitivities with MMJ classification and provenance; (2) a first real dataset for the **Banking & Financial Services** sector (at least fifteen NSE-listed banks, every instrument fully covered across all eight factors); (3) authenticated HTTP APIs to query a single sensitivity (with **freshness** metadata) and an admin-only **matrix** view; and (4) an internal **`/admin/factor-db`** page for the Product Owner to review the matrix, with access restricted by an email allow-list consistent with Phase 1’s “no public route auth for mainstream surfaces” posture.

**How it fits into the overall application**

This is the analytical backbone slice referenced in the PRD as Tier 1 data. It unblocks downstream stories that consume factor sensitivities when drafting or validating Event Intelligence Cards (for example the LLM synthesis pipeline and Evidence-layer checks). It is intentionally scoped to **one sector** in Phase 1 to limit blast radius while still enabling end-to-end pipeline testing.

**Functional breakdown**

- **Write path:** Schema and seed are applied via SQL migrations/seeds (not PostgREST for bulk load). Runtime reads use **direct PostgreSQL** from the backend when `SUPABASE_DB_URL` is configured.
- **Read path (sensitivity):** Resolve instrument by NSE ticker + factor slug; return signed sensitivity, MMJ tag, source URL, `retrieved_at` ISO timestamp, and computed **freshness**.
- **Read path (matrix):** For a sector slug (default `banking`), return sector metadata, ordered factors, instruments in that sector, and a nested map `ticker → factor_slug → cell` including freshness per cell.

**Edge cases, validations, and error handling**

- Missing DB URL: sensitivity and matrix paths return **503** from the service layer when the connection cannot be opened.
- Unknown instrument/factor pair: sensitivity returns **404**.
- Matrix for unknown sector slug: **404** with lookup error detail.
- Empty `FACTOR_DB_ADMIN_EMAILS`: matrix endpoint denies everyone (**403**); admin page shows configuration guidance instead of the grid.
- RLS enabled on factor DB tables with **no permissive policies** for `anon`/`authenticated`, so accidental exposure via PostgREST is avoided; backend uses the database connection string (service-level access).

**Business rules enforced**

- Every sensitivity row must have **MEASURED | MODELLED | JUDGED** (`mmj_type`) and a **non-empty** `source_url` (CHECK + type).
- **Phase 1** does not store amounts or end-user holdings here; this is **sector/instrument reference data** for cards.
- ⚠️ Seed content is **methodologically conservative** (deterministic hashing for demo cells); it is **not** a substitute for discretionary investment advice. Product Owner review of actual sourcing remains a separate editorial activity.

### A3. DECISIONS MADE DURING EXECUTION

| Decision | Rationale | Alternatives not chosen |
|----------|-----------|-------------------------|
| **Migration file `0007_factor_db.sql`** (not `0006_*`) | Repository already had `0006_events_dedupe_newsapi_quota.sql`. Renumbered factor migration to **0007** to preserve apply order. | Colliding filenames rejected. |
| **`psycopg` in main backend dependencies** | Factor DB reads are server-side SQL; mirrors pattern used by integration tests (`supabase_db_url`). | Supabase REST-only: would require exposing tables and policies; rejected for tighter control and simpler constraints. |
| **Signed integer −5…+5 for sensitivity** | Compact, sortable, easy for UI and LLM grounding; direction + magnitude in one field. | Text enums (“high/low”): harder to combine programmatically. |
| **Freshness from `retrieved_at` only** | Matches PRD Evidence “freshness dot” narrative; no separate “reviewed_at” in P1-S5. | Per-factor TTL tables: deferred. |
| **Admin = env allow-list, not RBAC roles** | Phase 1 defers full RBAC; matches “internal PO tools” and ships quickly. | Supabase custom claims / `roles` table: future hardening. |
| **Next.js page shows forbidden content vs HTTP 403** | App Router server component fetch to API returns 403 JSON; page renders an explicit forbidden message. True **browser HTTP 403** for the document itself would need a route handler or middleware matcher (optional polish). | Blocking PR: unacceptable UX. |

**Assumptions**

- `SUPABASE_DB_URL` is available to the backend in every deployed environment that should serve Factor DB APIs.
- The same person who can deploy SQL migrations will run **`0007`** then **`banking_sector.sql`** on Supabase (or equivalent pipeline).

**⚠️ Critical: do not reverse without impact analysis**

- **MMJ + source URL on every cell** is a compliance-facing invariant for Evidence; loosening constraints breaks PRD §6.x traceability promises.
- **Empty admin allow-list** intentionally **denies** matrix access (fail closed for admin-only data).

## PART B — EXTENDED REFERENCE

### B1. DATABASE / DATA MODEL CHANGES

**Tables (migration `0007_factor_db.sql`)**

- **`sectors`:** `id` UUID PK, `slug` UNIQUE, `name`, `created_at`.
- **`factors`:** `id` UUID PK, `slug` UNIQUE, `display_name`, `description`, `sort_order` UNIQUE 1–8, `created_at`.
- **`instruments`:** `id` UUID PK, `sector_id` FK → `sectors`, `ticker`, `exchange` (default `NSE`), `isin`, `display_name`, UNIQUE(`exchange`,`ticker`), `created_at`.
- **`instrument_factor_sensitivity`:** PK(`instrument_id`,`factor_id`), FKs to `instruments` / `factors`, `sensitivity` SMALLINT CHECK −5…5, `mmj_tag` `mmj_type` NOT NULL, `source_url` NOT NULL with trim check, `retrieved_at` TIMESTAMPTZ NOT NULL.

**RLS:** Enabled on all four tables; **no** `SELECT` policies for anon/authenticated → not browseable via PostgREST without service role.

**Sequencing:** Run after enums + core migrations; in-repo order is `0003` → `0004` → `0005` → `0006_events_dedupe_newsapi_quota.sql` → **`0007_factor_db.sql`**.

**Seed:** `banking_sector.sql` — idempotent upserts; can be re-applied after edits.

---

### B2. API / INTEGRATION CONTRACTS

**Base path:** FastAPI app includes router at `/api`, router prefix `/factor-db` → full path `/api/factor-db/...`.

| Method | Route | Query / body | Auth | Success response |
|--------|--------|----------------|------|------------------|
| GET | `/api/factor-db/sensitivity` | `instrument` (ticker), `factor` (slug) | Bearer required | `SensitivityResponse` JSON |
| GET | `/api/factor-db/matrix` | `sector` (default `banking`) | Bearer + admin email | `MatrixResponse` JSON |

**Example sensitivity response (illustrative)**

```json
{
  "instrument_ticker": "SBIN",
  "factor_slug": "crude_oil",
  "instrument_display_name": "State Bank of India",
  "sensitivity": -2,
  "mmj_tag": "JUDGED",
  "source_url": "https://pib.gov.in/Pressreleaseshare.aspx",
  "retrieved_at": "2026-03-15T06:30:00+00:00",
  "freshness": "green"
}
```

**Matrix payload shape (illustrative):** `sector` object, `factors` array, `instruments` array, `sensitivities` map `ticker → factor_slug → { sensitivity, mmj_tag, source_url, retrieved_at, freshness }`.

---

### B3. BUSINESS LOGIC & RULES (Detailed)

- **Ticker match:** Normalized to upper for NSE lookup in `lookup_sensitivity`.
- **Factor match:** Slug compared lowercase.
- **Freshness:** Compare `reference_now − retrieved_at` in days to thresholds derived from `round(365.25 × 0.5)` (green) and `round(365.25 × 1.5)` (amber); remainder red. Reference defaults to **UTC now** for matrix generation.
- **Admin check:** Email must appear in comma-separated `FACTOR_DB_ADMIN_EMAILS` (case-insensitive, trimmed). If env is empty, **no one** passes admin for matrix.

---

### B4. KNOWN CONSTRAINTS & TECH DEBT

- Seed sensitivities are **algorithmically varied** for coverage and testing, not a **Research-validated** bank/factor matrix. ⚠️ Replace with analyst-reviewed values before treating as production research output.
- Admin gating duplicates allow-list in **frontend** (UX) and **backend** (security). A single source of truth service-side only would still need the frontend to know “can open page” — acceptable duplication for P1.
- Browser **navigation** to `/admin/factor-db` may still return HTTP 200 with a forbidden **message**; true **403 status** on the HTML response is optional follow-up.
